# Data Contract: `searchreceipt/v0.1`

## Authority and evolution

`src/schemas.ts` is the authoritative runtime contract. `schemas/*.schema.json` is generated for interoperability. Runtime checks include cross-field refinements—unique IDs, existing evidence references, fixture honesty, status/hash semantics, issue derivation, and result consistency—that JSON Schema draft 7 may not fully encode. Future incompatible formats use a new `schemaVersion`; v0.1 performs no implicit migration.

Before schema validation, file inputs pass through a strict raw parser. It rejects duplicate decoded member names at every object depth, including names made equal by JSON escapes, and rejects the prototype-sensitive names `__proto__`, `constructor`, and `prototype`. Native last-key-wins behavior is never used as an ambiguity boundary.

## Canonicalization and integrity

`searchreceipt-jcs/v0.1` recursively sorts Unicode property names using JavaScript's default string ordering, preserves array order, and serializes with `JSON.stringify` without whitespace. v0.1 inputs contain only JSON-safe schema values. The receipt hash is:

```text
"sha256:" + hex(SHA-256(canonical-json(receipt excluding integrity)))
```

This is a project-specific deterministic profile, not a claim of full RFC 8785 conformance.

The stored demo receipt is generated by the shipped CLI and intentionally ignored by Prettier because its compact recursive key order is part of the canonical bytes. A built-CLI regression compares the stored bytes and SHA-256 with a fresh `create` result.

## Provenance

`createdAt`, `retrievedAt`, `capturedAt`, and `observedAt` are RFC 3339 timestamps supplied by the caller. SearchReceipt does not attest their accuracy. `method: fixture/demo` requires `benchmark: false`.

## Evidence

Every evidence entry has a unique `id`, a SHA-256 `contentHash`, and optionally a relative POSIX `contentPath` to a local snapshot. Evidence kinds:

- `web`: HTTPS URI, retrieval timestamp, optional title;
- `file`: relative path and capture timestamp; its `path` is the default snapshot path;
- `solanaTransaction`: cluster, base58 transaction signature, slot, observation time;
- `solanaAccount`: cluster, base58 account address, optional owner program, slot, observation time;
- `solanaProgram`: cluster, base58 program ID, optional deployment slot, observation time.

These identifiers are references, not chain-validity attestations. Base58 syntax/length checks do not establish curve ownership, deployment state, finality, or canonical history.

## Claims and policy

Claim IDs are unique. Each claim must contain at least one unique `evidenceRef`, and every reference must resolve. `requireClaimEvidence` is fixed to `true`; `allowedHashAlgorithms` is exactly `["sha256"]`. `requireLocalContent` controls whether every evidence entry must be backed by a verified local snapshot.

## Verification result

`passed` requires valid receipt integrity, valid claim references, no mismatched content checks, and no verification issues. `contentChecks` is non-empty and has unique evidence IDs. `verified` requires equal present actual/expected hashes; `unavailable` forbids an actual hash; `mismatch` requires unequal hashes or a missing actual hash and a corresponding explained issue. Integrity/claim flags and issue presence must agree. Every result carries the receipt's embedded `receiptHash` and this fixed assurance boundary:

> Internal integrity and supplied local snapshots only; external truth is not established.

`verified` content means local bytes matched. `unavailable` means no root/path was supplied. `mismatch` includes a hash mismatch or safely refused/unreadable path.

`verificationResultSchema` enforces standalone internal invariants. `validateVerificationResult(receipt, result)` is the receipt-aware runtime API: it requires exact ordered one-to-one evidence ID/hash coverage, matching receipt ID/hash and integrity, and issue behavior consistent with `requireLocalContent`. The generated draft-7 schema is structural and cannot encode all Zod refinements; it must not be treated as semantic certification. Neither schema parser performs content I/O or proves that a supplied `actualHash` was observed. `verifyReceipt` is the trusted execution path that reads supplied local snapshots and then applies the receipt-aware contract.
